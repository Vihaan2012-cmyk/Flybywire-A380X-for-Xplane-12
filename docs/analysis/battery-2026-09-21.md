## The strongest result: the interactions are predictable

Before running each tier the harness predicts its outcome from the tiers
below it, then checks. Every tier: **100 % right, 0 failures foreseen,
0 missed, 0 false alarms** — including tier 5's 1,000 random 5-to-12-fault
combinations predicted from tiers 1-4. Nothing emergent appeared at depth.
For a model of this size that is the interesting finding, not the zero
failure count.

## The 23,261 composition flags, triaged

The harness flags a combination when a part's own effects are not all
present with the others armed, and says so plainly: "physical masking or a
bug". 23,261 combinations are flagged and `TIERS.txt` lists the first 300.
Of those 300:

- **43** are two electrical items (bus, TR, generator, battery, or an ATA-24
  failure id). Masking is expected: fail AC1 and AC ESS SHED together and
  most of AC ESS SHED's downstream effects are already gone.
- **130** pair one electrical item with something else. Same shape.
- **127** my first pass classified as neither, wrongly — the group is
  dominated by `24100`/`24101`/`24105`, which *are* electrical failure ids
  (they have no component name, so a name-based filter misses them), and by
  `gear-actuator-*` / `gear-door-actuator-*` pairs.

The gear-actuator group is worth understanding because it shows the
composition rule's blind spot rather than a defect. Pulling a gear
actuator's breaker removes a load, which moves `A32NX_ELEC_AC_1_BUS_POTENTIAL`
slightly. Pull a second one and the bus potential has already moved, so the
second breaker's "effect" on it is absent. The union rule cannot hold for a
**shared continuous quantity two loads both influence**. `AC_1_BUS_POTENTIAL`
and `AC_2_BUS_POTENTIAL` head the masked-variable list at 66 occurrences
each, which is this effect and not a bug.

### Worth a real look

One class does not reduce to shared-quantity masking:

```
bleed-eng-1,pack-1-flow-valve-1 -- bleed-eng-1: 11 effects gone
  (A32NX_COND_PACK_1_ACM_PRESSURE_RATIO, A32NX_ENGINE_BLEED_EXTRACTION_KG_S:1,
   A32NX_ENGINE_EGT:1, ...); pack-1-flow-valve-1: 12 effects gone
```

An engine-bleed failure losing its effect on that engine's **EGT** when a
pack flow valve is also failed is plausible physically (no extraction, no
EGT change) but it crosses from the air system into the engine's gas path,
which is exactly where a genuine coupling bug would hide. The
`bleed-eng-{1,2}` × `pack-1-flow-valve-{1,2}` block is small and specific
enough to settle by reading. `A32NX_PNEU_ENG_2_INTERMEDIATE_TRANSDUCER_PRESSURE`
appears 33 times across the flags and belongs to the same area.

## Throughput, and the estimate I got wrong

Sustained **4.1 cases/s** averaged over the run, not the ~50/s asked for and
not the 33/s I measured in the first minutes. Both earlier figures were
taken while tier 1 was running, whose cases are trivial. Deeper tiers run
far more ticks each — tier 5 averaged 5.6 s per case. Case rate is not a
property of the machine here; it is a property of the tier. 20 workers on
24 physical cores was the right size (per-worker rate fell from 2.78/s at
4 workers to 1.65/s at 20, so more workers would have bought little).

## Reproducing

```
battery.exe --tiered --workers 20 --master-seed 20260921 \
            --dump-dir <out>/dumps --claim-dir <out>/claim \
            --timeout-secs 60 --max-gb 800
```

Worker **processes**, not threads, because the failure, breaker, circuit and
invariant state is process-global. That is the same hazard that was silently
corrupting the unit-test suite until nine tests were made to take the serial
lock (`5eaa016`); the battery had it right from the start.
